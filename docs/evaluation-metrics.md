# 全链路评测指标与 baseline 设计

日期：2026-10-26。本文是实验设计，不包含已测量的 baseline 分数。
两页 proposal 保留主指标，完整定义、分母和采集方法放在这里。

## 1. 主结论与指标分工

本项目需要同时回答三个问题：购物建议是否可行且算得对，事实是否有证据，
完成一次购物任务需要多少时间和资源。不能用单一 RAG 分数代替任务成功率，
也不能用模型生成速度代替用户拿到完整建议的速度。

建议主结果表只放四列：**TSR、Faithfulness、BVR、用户请求 p95 耗时**。
检索、工具调用和模型性能指标用于解释主结果，避免两页 proposal 堆满缩写。

| 环节 | 优先指标 | 辅助诊断 | 主要依据 |
| --- | --- | --- | --- |
| SerpApi 采集与知识库 | 必需字段覆盖率、来源一致率、价格年龄 | 采集成功率、重复率、API 调用量、限流率、冷/热缓存耗时 | 原 proposal 的知识库审计，加上采集与刷新成本 |
| 检索 | Recall@5、MRR@5 | Ragas Context Precision、Context Recall、检索耗时、上下文 token 数 | 原 proposal + Ragas |
| 回答与引用 | Faithfulness、引用支持率/覆盖率 | Factual Correctness、不可回答问题中的无依据作答率 | 原 proposal + Ragas |
| Agent 与预算 | TSR、BVR、金额错误率 | 硬约束违反率、schema 合法率、Tool Call Accuracy、偏好匹配 1-5 分 | 原 proposal + Ragas 工具指标；预算由确定性规则评判 |
| 推理服务 | TTFT、TPOT、输出 token/s、总显存峰值 | ITL、request/s、SLO goodput、排队时间、启动时间 | vLLM 性能测量体系 |
| 用户全流程 | p50/p95 完整请求耗时、任务成功率、失败率 | 每个成功任务的 API/LLM 调用数、tokens、费用；重试与桥接等待 | 项目自定义端到端观测 |

## 2. 采集与知识库指标

这些指标使用确定性校验和人工抽查，不要求 LLM 裁判。

- **必需字段覆盖率**：按商品类别定义必需属性，统计有效观测字段数 / 应有必需字段数。
  单独报告价格、币种、规格、配送信息等字段覆盖率；不把不可返回的评论文本当成已采集。
- **来源一致率**：人工核对的字段中，与存档来源一致的字段占比。保留抽样规则与样本数，
  区分与快照一致、与当前网页一致两个问题。
- **价格年龄**：评测时刻减去价格观测/来源时间，按 p50/p95 或年龄区间报告；
  来源时间未知就记 unknown，不能把“刚写入 SQLite”解释成“刚更新的价格”。
- **重复率**：规范化与去重前的记录数为分母，报告被认定为重复的记录占比；
  不同规格、商家报价和冲突证据不能作为重复直接删除。
- **采集成本和失败**：每次 HTTP 尝试计数，分别记录实际刷新、缓存命中、限流、
  超时、无法解析和缺少字段。供应商计费口径与本地 HTTP 次数分开报告。

线上刷新和冻结快照回放是两组实验；冻结回放不应被描述成实时 SerpApi 请求。

## 3. 检索指标与 Ragas 的区别

令每个查询的人工相关证据集合为 `R`，检索前五条证据 ID 集合为 `D5`：

- `Recall@5 = |R intersect D5| / |R|`。
- `MRR@5 = mean(1 / first_relevant_rank)`；前五条无相关证据时贡献为 0。
- 对没有相关证据的查询，Recall/MRR 记为不适用，另算不可回答问题上的错误作答率。
  不得把空参考集的召回率默认记为 1。

这两个指标优先用冻结快照中的稳定 evidence ID 和人工相关性标签计算。
人工相关性不应只标注某个检索器返回的结果；小规模试验可对完整快照或多检索器候选池
补充审核，避免把漏标相关证据当作错误。

Ragas 的 **Context Precision** 关注相关上下文是否排在前面，带有排序权重，
不等同于普通 `Precision@5`。固定使用前五条、相同证据粒度和相同参考事实，
记录所用实现与裁判。[官方定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)

**Context Recall** 的 LLM 版本衡量参考答案中的事实被检索上下文覆盖的程度；
ID 版本则检查参考证据 ID 的覆盖。两者不能在结果表中混写成同一个召回率。
本项目将 ID Recall@5 作为主指标，事实覆盖作为补充诊断。
[官方定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)

## 4. 回答与引用指标

**Faithfulness**：回答中的事实是否能由实际提供给模型的证据支持。
分母是回答中可评判的事实声明数；没有事实声明时记不适用，并结合 TSR 检查是否回避任务。
评测上下文必须包含共同提供的结构化商品事实及实际检索片段。
高分只能说明忠实于输入，不能证明过期价格今天仍有效。
[Ragas Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)

**Factual Correctness**：相对于审核过的参考事实，检查回答事实的 precision/recall/F1。
购物任务可能有多个正确商品组合，因此参考资料应按所推荐的商品及必要解释组织，
而不是把某一个“标准购物篮”的措辞作为唯一正确答案。
[Ragas Factual Correctness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/factual_correctness/)

另外用证据 ID 检查引用是否存在，以及所引用内容是否支持对应声明：

- **引用支持率**：被有效来源支持的已引用声明数 / 所有已引用声明数。
- **引用覆盖率**：带有有效支持引用的应引用声明数 / 所有应引用声明数。
- **无依据作答率**：不可回答测试中仍输出无证据结论的案例数 / 不可回答案例数。

引用 ID 能解析不代表它支持声明；支持关系仍需事实核对或经人工校准的裁判。
Ragas 裁判模型、提示词、版本、随机设置和失败记录需要固定；
在两位人工评审标注的样本上检查偏差。裁判失败不能悄悄当作零分或被丢弃。

## 5. Agent、预算与实际任务成功

### 主要指标

`TSR = 成功完成的测试运行数 / 全部测试运行数`。

按测试类型定义成功：可回答任务给出满足硬约束、成本正确的计划；
无可行解任务正确说明冻结候选目录中不存在可行计划；缺少必要输入的任务提出必要澄清。
可正常作答却无必要地拒答、随意追问、超时和崩溃都算失败。
另报各类别成功率，避免总分掩盖某类任务失败。

`BVR = 超出真实可用预算的已交付计划数 / 全部已交付购买计划数`。

同时报告分子、分母和 TSR。没有交付任何计划时 BVR 为不适用，不能声称零违规。
若展示多个候选购物篮，逐篮统计并另外给出“至少一个违规篮”的任务占比。
缺少必要费用却声称已满足预算，属于未经证实的可行性声明并使任务失败。

- **金额错误率**：已给出的可核算金额中，和独立 Decimal 校验不一致的占比；
  价格、税费、配送、数量、余额分项检查。可另报绝对误差，按币种分开统计。
- **硬约束违反率**：已交付计划中违反至少一项必需规格/数量/约束的占比。
- **偏好匹配**：两位评审按固定 1-5 分标准独立评分，报告分布和评审一致性；
  不用主观偏好得分覆盖预算违规。

### 工具使用

schema 合法率只检查参数格式；执行成功率检查工具是否运行成功；二者均不代表
工具选得正确。Ragas **Tool Call Accuracy** 可比较预期工具、参数及调用顺序。
若存在多种有效路径或可并行调用，应预先允许等价路径/合理顺序，而非强制唯一轨迹。
[Ragas 工具指标](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/agents/)

本项目的确定性 TSR 是主结果。Ragas Agent Goal Accuracy 可以辅助人工审阅，
但不应替代独立预算与规格检查。

## 6. vLLM 指标与当前代码的测量边界

采用与实际安装版本相符的 `vllm bench serve` 或等价 SSE 测量程序。
不要直接照搬 latest 文档的参数而假设课程环境的 vLLM 0.26.0 全部支持。

| 指标 | 计时边界或分母 | 报告方式 |
| --- | --- | --- |
| TTFT | 发出模型请求到接收首个有效流式输出 | 毫秒；p50/p95；说明是否包括模型端队列 |
| TPOT | `(request_latency - TTFT) / (output_tokens - 1)` | 毫秒/token；输出不超过一个 token 时单独处理并注明工具约定 |
| ITL | 相邻流式输出到达的间隔 | 毫秒；token 与流式 chunk 不总是一一对应 |
| 输出吞吐 | 完成请求的输出 token 总量 / 观测窗口时长 | output token/s，不能和 input+output token/s 混用 |
| 请求吞吐 | 成功完成的模型请求数 / 观测窗口时长 | request/s；同时报告尝试数、失败率与并发 |

TTFT、TPOT、ITL 的边界和输出分块语义参照
[vLLM Benchmark CLI](https://docs.vllm.ai/en/latest/benchmarking/cli/)。

**SLO goodput**：每秒满足预先确定的 TTFT/TPOT 或请求总延迟阈值的模型请求数。
阈值从开发阶段确定并冻结，不能看了测试结果后再调；goodput 必须与原始吞吐、
失败和丢弃率一起看。[vLLM goodput 参数](https://docs.vllm.ai/en/latest/cli/bench/serve/)

**资源**：逐 GPU 记录服务进程/分配的总显存峰值，注明权重、KV cache 和运行时分配；
不能把日志中的权重显存作为服务总显存。GPU 利用率是解释指标，不能单独证明效率。
记录模型启动、预热、冷/热缓存和并发条件；统计基准的缓存策略必须一致。

当前 `qwen_client.chat()` 没有发送 `stream=true`，只在完整 JSON 响应返回后结束。
因此现有测试可测完整 HTTP 耗时，**无法测 TTFT、TPOT 或 ITL**。
SDK 文件桥接若仅返回最终结果，用户首个可见响应也不会等于模型 TTFT。

## 7. 全流程延迟、成本与 trace

- **用户完整请求延迟**：后端接受请求至可展示最终计划的持续时间；
  浏览器侧再记录点击至呈现的用户时间，用于区分前端与网络开销。
- **任务 goodput**（项目自定义）：每秒同时满足任务正确性和完整任务时限的任务数。
  它和 vLLM 的模型请求 goodput 属于不同层级，不能混报。
- **每成功任务成本**：评测窗口内所有任务的实际服务费用 / 成功任务数，
  分子包含失败、重试与补采。没有成功任务时为不适用；没有真实计费数据时只报
  API 次数、tokens 和 GPU-seconds，不能编造美元价格。
- **失败率**：分别报告 API、桥接、模型、工具、评测裁判和用户任务失败。
  不把不完整或失败请求从报告中删除；成功请求延迟分布与超时计数分别呈现。

以一个 request ID 关联 `acquire`、`bridge_upload`、`worker_wait`、`retrieve`、
`llm_request`、`tool_execute`、`bridge_download`、`present` 等 span。
每个 span 存父 ID、起止时间、状态、重试次数、snapshot/model ID、token/call counts。
凭据与个人预算明细不写入公开 trace。

本地耗时使用单调时钟，不直接相减两台未同步机器的墙钟。并行任务应分析关键路径，
不能把所有子步骤时长相加当作端到端耗时。重复网络等待、模型端队列和 SDK 轮询
应分别定位，避免把同一时间算两次。

## 8. Baseline 和消融的可解释性

| 配置 | 额外文本证据 | 执行方式 | 预算校验工具 | 主要比较 |
| --- | --- | --- | --- | --- |
| B0 Single call | 无；仍有共同的结构化候选与价格 | 单次模型调用 | 无 | 检索前的基线 |
| B1 Keyword RAG | 同一证据池的 FTS5 结果 | 单次调用 | 无 | B0/B1：增加文本检索 |
| B2 Structured RAG | 在同一候选池做过滤与 FTS5 检索 | 单次调用 | 无 | B1/B2：检索策略 |
| B3 Full advisor | 与 B2 相同的检索策略 | 有界多步工具循环 | 有 | B2/B3：完整 Agent 栈的整体增益 |
| A1 Without loop | 与 B3 相同 | 一次计划后执行同类工具，不迭代修正 | 有 | B3/A1：循环与恢复能力 |
| A2 Without validator | 与 B3 相同 | 多步循环 | 无 | B3/A2：预算工具贡献 |

所有配置仍由同一个独立校验器打分。关闭系统里的 validator，不等于关闭评测检查。
检索对照固定结构化候选、价格、文本池、模型和生成设置；
未过滤上下文实验说明上下文长度/截断规则，不能让额外 token 预算成为隐藏变量。
不把 B2/B3 的改善全部归因于“多轮”，因为它还增加了预算工具。

其他实验分组运行，不做所有维度的笛卡尔积：

1. 同一基础模型的 base/SFT，可选 DPO；公共 27B INT4 只作为部署参照。
2. 同一选定 checkpoint 的高精度/INT8/INT4，固定 tokenizer 与生成设置。
3. 同一模型和服务上的顺序/两路分析、过滤/未过滤上下文、缓存/执行模式；
   每次只改变一个因素，记录输出长度、并发、token 上限和冷/热缓存状态。

按原 proposal 运行 10 个开发案例、40 个测试案例，每个核心配置重复三次，
包含冻结后加入的第五类别的 8 个案例。三次重复不是三个独立的新任务；
区间估计应按案例成组重采样，并报告每类结果和配对差异。
保留零预算/金额错误目标，以及降低 20% 中位时延或 30% 输入 tokens、
成功率下降不超过 5 个百分点的效率目标。这些仍是目标而非结果。

## 9. 两页 proposal 的图表选择

第一页保留主架构图和压缩后的数据/实施说明。第二页采用论文式三线表：
baseline/消融及四个主结果列；另一张表解释六个环节的测量。
`n/m` 表示尚未测量，不代表零分、没有提升或不适用。

有真实结果后，建议在实验报告中加入：

- **质量-延迟散点图**：x 为用户中位延迟，y 为 TSR；按配置标注，呈现真实取舍。
- **延迟关键路径图**：由实际 traces 展示桥接、采集、模型与工具等待，
  并行部分使用时间线；不要把重叠 span 画成可加总堆叠柱。
- **量化取舍图**：同一模型的总显存与 TSR/faithfulness，附案例级不确定性。

在尚无测量结果的 proposal 中，baseline 设计表比虚构性能柱状图或预期收益曲线更可信。
